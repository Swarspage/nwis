# NWIS Canonical Telemetry Schema — v0.1.0

> **Status**: MVP/Prototype — Schema `0.1.0`  
> **Last updated**: 2026-09-01  
> **Source of truth**: [`schemas/nwis_telemetry.schema.json`](../schemas/nwis_telemetry.schema.json)

---

## Purpose

The NWIS Canonical Telemetry Schema defines a single, shared internal data contract that all telemetry sources must conform to before entering the NWIS processing pipeline.

**This schema unifies:**

| Source Type | Example |
|---|---|
| Historical drilling telemetry | WELL-1 (VLOVE system) |
| Synthetic demo wells | NWIS Simulator |
| Future live feeds | eRTMAC / OIL integration |

**The single-pipeline architecture eliminates a "real pipeline" vs "demo pipeline" split.** The simulator is simply another source adapter. Every record downstream is identical in structure, regardless of origin.

---

## Architecture

```
RAW / SYNTHETIC INPUT
        │
        ▼
  SOURCE ADAPTER
  (per source: VLOVE, eRTMAC, NWIS_SIMULATOR, ...)
        │  Reads source format
        │  Applies source mapping (well1_canonical_mapping.json)
        │  Emits canonical records
        ▼
NWIS CANONICAL SCHEMA (this document)
        │
        ▼
  FEATURE ENGINE
  (normalization, windowed features, derived signals)
        │
        ▼
  INTELLIGENCE LAYER
  (pattern recognition, anomaly scoring — NOT YET BUILT)
        │
        ▼
       API
        │
        ▼
   DASHBOARD
```

> **Key invariant**: Any component downstream of SOURCE ADAPTER must never receive source-specific channel names or raw format structures. It receives only canonical records.

---

## Schema Version

**Current version**: `0.1.0`

This is a prototype schema. It will evolve. Schema versioning follows Semantic Versioning:

- `MAJOR` bump: breaking field removals or incompatible type changes
- `MINOR` bump: new fields added in a backward-compatible way
- `PATCH` bump: documentation corrections, no structural change

Every canonical record carries `schema_version` so downstream consumers can gate on compatibility.

## Record Structure

### Record Metadata (always required)

| Field | Type | Nullable | Description |
|---|---|---|---|
| `schema_version` | string | No | Must be `"0.1.0"` |
| `timestamp` | ISO-8601 datetime | No | UTC timestamp of the telemetry sample |
| `well_id` | string | No | Internal NWIS well identifier |
| `source_system` | string | No | Source system identifier (e.g. `VLOVE`, `NWIS_SIMULATOR`) |
| `source_well_id` | string | No | Original well ID in the source system |
| `source_row_index` | integer | Yes | Zero-based row index in source file (null for streams) |
| `data_origin` | enum | No | See Data Origin Values |
| `telemetry_status` | enum | No | See Telemetry Status Values |

### Measurements

Each measurement is an object with:

| Sub-field | Type | Nullable | Description |
|---|---|---|---|
| `value` | number | **Yes** | Measured value. **Null = missing. Zero = zero.** Never conflate them. |
| `unit` | string | Yes | Physical unit. Null if unknown. Do not invent units. |
| `unit_status` | enum | No | `VERIFIED` / `ASSUMED` / `UNKNOWN` |
| `source_channel` | string | Yes | Original source channel name. Always preserved for HISTORICAL_SOURCE records. |
| `quality` | enum | No | See Quality Values |

### Canonical Measurement Fields

| Canonical Field | Description | WELL-1 Source Channel | WELL-1 Status |
|---|---|---|---|
| `depth` | Drilling depth | *(none)* | **UNMAPPED** — No verified continuous depth candidate in WELL-1 dataset window |
| `rate_of_penetration` | ROP | `GS_ROP` | CONSTANT_WINDOW (1 unique value) |
| `weight_on_bit` | WOB | `GS_SWOB` | ZERO (locked at 0.0 — this is a valid zero, not missing) |
| `rotary_speed` | Surface RPM | `GS_RPM` | UNVERIFIED |
| `torque` | Surface torque | `GS_TQA` | UNVERIFIED — negative values observed, physical interpretation unclear |
| `standpipe_pressure` | Pump pressure | `GS_SPPA` | UNVERIFIED — 45.22% negative values, anomalous |
| `flow_rate` | Total flow | `GS_TFLO` | UNVERIFIED — 97.9% zeros in this window |
| `hookload` | Hook load | `GS_HKLD` | UNVERIFIED — most dynamic channel in WELL-1 |
| `block_position` | Travelling block | `GS_BPOS` | UNVERIFIED |

## Data Origin Values

| Value | Meaning |
|---|---|
| `HISTORICAL_SOURCE` | Derived from real archived telemetry (e.g. WELL-1 VLOVE data) |
| `SYNTHETIC_DEMO` | Generated by the NWIS Simulator for demonstration/development |
| `FUTURE_LIVE_SOURCE` | Reserved for future real-time eRTMAC / OIL feeds |

> **Critical**: Every downstream component — including the dashboard — must be able to display `data_origin` to users. **Synthetic data must never be presented as historical real data.**

---

## Telemetry Status Values (record-level)

| Value | Meaning |
|---|---|
| `VALID` | Record has at least one usable measurement |
| `PARTIAL` | Record has some valid measurements, some missing |
| `SOURCE_GAP` | Record is immediately adjacent to a detected time gap in source |
| `EMPTY` | All measurements are null |
| `DATA_ARTIFACT` | Record is flagged suspect due to source data quality issues |

---

## Quality Values (per-measurement)

| Value | Meaning |
|---|---|
| `VALID` | Value is plausible and passes basic range checks |
| `MISSING` | Value is null — sensor not reporting |
| `SOURCE_GAP` | Value is in a record adjacent to a detected source time gap |
| `INVALID_SOURCE_VALUE` | Value is present but physically implausible (e.g. extreme outlier) |
| `UNVERIFIED` | Mapping or unit has not been validated from source documentation |
| `CONSTANT_WINDOW` | Channel is constant for the entire dataset window — informationally useless in this slice |
| `ZERO` | Value is exactly 0.0 — explicitly distinguished from MISSING |

> **Invariant**: A `MISSING` quality must have `value: null`. A `ZERO` quality must have `value: 0`. These must never be swapped.

---

## Units Policy

**All units for WELL-1 (VLOVE) channels are `UNKNOWN`.**

VLOVE channel documentation has not been independently verified as part of this MVP. No units are assumed or invented.

Units will only be set to `VERIFIED` when confirmed from:
- Official VLOVE/eRTMAC channel dictionary
- Source data documentation with explicit unit metadata
- Cross-verification against an independent source

---

## Depth Semantics

The `depth` canonical field is **explicitly nullable** in this schema.

**Reasons depth is unmapped for WELL-1:**
- `DBTM`, `DMEA`, `DEPT`, `SRVDEPTH`: 100% missing in the WELL-1 window
- `GS_DMEA`, `GS_DVER`, `GS_DRTM`: functionally constant — consistent with static well metadata, not a moving bit depth
- `GS_DBTM`: 5 unique values, median constant run ~7,324 seconds — behaves like a discrete step variable, not continuous depth
- `GS_TDH`: 90.9% coverage, but predominantly negative values — physical interpretation unclear

**The NWIS MVP does not claim to have a valid bit-depth channel from WELL-1.**

## Provenance Requirements

Every canonical record must be traceable. For `HISTORICAL_SOURCE` records, the following must be populated:

```json
{
  "source_system":    "VLOVE",
  "source_well_id":   "WELL-1",
  "source_row_index": 4271,
  "timestamp":        "2008-12-21T17:21:32Z",
  "measurements": {
    "hookload": {
      "source_channel": "GS_HKLD",
      ...
    }
  }
}
```

`source_channel` must never be discarded. It is the link back to the raw data file.

---

## Telemetry Gap Handling (WELL-1 Specific)

WELL-1 contains a **~8.2-hour gap** between `2008-12-21T19:42:00Z` and `2008-12-22T03:53:32Z`.

Handling rules:
- The record immediately **before** the gap: `telemetry_status: "VALID"` (last good record)
- The record immediately **after** the gap: `telemetry_status: "SOURCE_GAP"`
- Channels that become NaN after the gap (`GS_RPM`, `GS_TQA`, `GS_HKLD`): `quality: "SOURCE_GAP"`

---

## Future Simulator Contract

When the NWIS Simulator is built, it must:

1. Emit records conforming exactly to this JSON schema
2. Always set `data_origin: "SYNTHETIC_DEMO"`
3. Always set `source_system: "NWIS_SIMULATOR"`
4. Preserve source channel naming convention (may use the same `GS_*` names for VLOVE-replay mode or define new synthetic channel names)
5. **Not** introduce a separate simplified data format
6. Pass through the same canonical validator used for HISTORICAL_SOURCE records

The simulator is a source adapter. From the Feature Engine onward, it is indistinguishable in structure (only in `data_origin`).
